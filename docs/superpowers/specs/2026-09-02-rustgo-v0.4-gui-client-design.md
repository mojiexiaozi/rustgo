# Rustgo V0.4 GUI Client Design

## 1. Purpose and scope

V0.4 adds a desktop GUI client, `rustgoc-gui`, for personal self-hosting operators who prefer a window to a terminal. The application embeds the existing `rustgoc` library in-process and renders connection state, tunnel health, local host telemetry, live logs, and P2P path selection. It is a viewer and connection switch, not a second client implementation: all protocol, relay, P2P, reconnection, and authentication behavior remains owned by the `rustgoc` crate.

V0.4 also makes two small library additions to `rustgoc` so an embedder can observe state that today only tracing output reveals: a public traffic snapshot accessor and a public P2P path-status store. Both are read-only projections of state the client already tracks internally.

Out of scope for V0.4: configuration editing in the GUI, client-side history persistence, an embedded server dashboard, tray integration on Linux, multi-profile management, auto-update, packaging/installers beyond `cargo build`, remote control of the GUI, and any server-side change. The headless `rustgoc` binary remains unchanged in behavior and remains the automation interface.

## 2. Compatibility and defaults

`rustgoc-gui` is a new workspace member and binary target. It adds no listener, no port, and no protocol message. V0.1/V0.2/V0.3 servers accept a V0.4 GUI client exactly as they accept the headless client, because the GUI drives the same `ClientApp` the binary drives.

The CLI follows the repository grammar: `rustgoc-gui` with no arguments is equivalent to `rustgoc-gui -c client.toml`. One additional flag, `--selfcheck`, runs the full runtime wiring headless against a configured server, prints one diagnostic line per observed state transition, and exits zero on success. Configuration loading, validation, environment interpolation, and `check_client_references` semantics are identical to `rustgoc`.

Missing or explicitly disabled client `[telemetry]` does not change GUI behavior: host sampling for the charts is a local GUI concern, independent of client telemetry reporting. Server negotiation still controls whether telemetry reports are sent to the server.

## 3. Architecture and ownership

The workspace gains one crate, `crates/rustgoc-gui`, with three strictly separated layers:

- **Runtime layer** (`runtime.rs`): owns a small Tokio multi-thread runtime (two workers), one `CancellationToken` per generation, and the spawned `ClientApp::run_until` task. Connect means "construct a `ClientApp` from config and respawn"; disconnect means "cancel and join". The GUI never blocks the UI thread on client work.
- **State layer** (`state/*`): display-free view models. `ConnectionViewModel` derives `Disconnected | Connecting | Connected { generation } | Backoff { seconds }` from the `watch::Receiver<ClientStatus>` plus local lifecycle observations; `TunnelRow` projects `RegisteredTunnel`; `LogRing` is a bounded tracing sink; `TelemetryHistory` is three bounded ring buffers fed by a `rustgo-observability` sampler; the P2P view polls the library's `PathStatusStore` version counter and clones only on change. Every state type is unit-testable without a window server.
- **Presentation layer** (`ui/*`, `main.rs`): an `eframe`/`egui` app with tabs for Connection, Telemetry, P2P, and Logs. The UI layer reads state only; all transitions live in the state layer. Watch updates wake the UI through `egui::Context::request_repaint` from background runtime tasks, with a 500 ms repaint floor as the poll backstop.

The client library gains:

- `TrafficSnapshot { sent_bytes, received_bytes }` with a `ClientApp::traffic_snapshot() -> Option<TrafficSnapshot>` accessor; `None` when telemetry is explicitly disabled.
- A `path_status` module owning `PathKindStatus::{Direct { address }, Relay}`, `PathStatus`, and `PathStatusStore` — a `Mutex<BTreeMap<export-name, PathStatus>>` plus an `AtomicU64` version for cheap change detection. The store is created by `ClientApp`, passed into the peer runtime, and updated at the existing promotion/fallback/teardown ownership boundaries in `orchestration.rs`. Recording is unconditional bookkeeping (an atomic map insert), never an await, and cannot alter path selection outcomes.

Log capture: the GUI installs its own bounded `tracing` subscriber (ring buffer of at most 1,000 formatted lines, drop-oldest). It never calls `rustgo_transport::logging::init_logging`; stderr formatting stays available behind `RUST_LOG` for headless runs.

## 4. Failure isolation and resource bounds

- Every GUI-owned collection is bounded: log ring 1,000 lines, each telemetry series 300 points, tray event channel 64 entries. Overflow drops oldest and increments an internal drop counter; nothing allocates without a ceiling.
- Client failures cannot wedge the window: a fail-stop `ClientError::PeerGenerationFailed`/`TaskJoin` surfaces as an error banner and returns the view model to `Disconnected`; reconnect-loop exits land in `Backoff` with the next delay shown.
- A closed window cancels the client token and joins the runtime before process exit; no orphaned sockets or child tasks.
- Telemetry sampling and chart repaint are subordinate to the UI: sampling errors mark the series unavailable rather than panicking; the sampler is cancelled with the runtime.
- The tray module compiles everywhere but does nothing off-Windows; Linux builds never link GTK, libappindicator, or any tray runtime.

## 5. Configuration and CLI

```text
rustgoc-gui [-c <path>] [--selfcheck]
```

- `-c <path>`: client configuration, default `client.toml`, resolved exactly like `rustgoc` (relative paths resolve from the file's directory; `${ENV}` interpolation applies).
- `--selfcheck`: headless verification mode. Installs the ring subscriber, loads and validates configuration, runs one client generation against the configured server, waits at most 30 seconds for an active status, prints traffic and path-status snapshots as single-line logs, cancels, joins, and exits 0 only if every step succeeded.
- No GUI-specific configuration file exists in V0.4. Window position and tab choice are not persisted.

## 6. Client library surface additions

`TrafficSnapshot` follows the bounded-report style of the telemetry module: plain copyable integers, saturating arithmetic upstream, no clocks. The accessor is cheap and lock-free (atomic loads).

`PathStatusStore` keys entries by export (forward) name. `record` stamps `updated_unix_millis` from the same monotonic-to-Unix conversion used elsewhere in the client. Transitions recorded: initial relay state when a path manager starts; `Direct { address }` on promotion and on authoritative direct selection; `Relay` on fallback after a direct attempt fails; removal when the session finishes. The store never records candidate addresses beyond the selected remote address and never records peer identity beyond what the export name already carries.

## 7. Connection management UI

The Connection tab shows:

- server address from config, current display state (disconnected, connecting, connected with generation number, or backing off with the retry delay);
- connect and disconnect buttons; connect is disabled while connected, disconnect while disconnected;
- the tunnel table: name, protocol, local address, remote port, accepted/rejected, and last error, projected from the active generation;
- live sent/received totals from `traffic_snapshot()`, or an explicit "counters disabled" note when telemetry is off;
- an error banner region for fail-stop errors and configuration problems.

Connecting and backing-off states are inferred locally from lifecycle observations; `ClientStatus` itself remains connected-or-not.

## 8. Telemetry charts

The Telemetry tab renders three egui_plot line charts — CPU, memory, network — from the local sampler at a fixed two-second interval, 300 points retained (ten minutes of history). The chart also plots client logical traffic rates derived from `traffic_snapshot()` deltas. Sampling is display-independent; charts render whatever history exists, and a freshly started window shows a short line rather than an error.

## 9. P2P path panel

The P2P tab lists one row per export: name, current kind (`Relay` or `Direct { address }`), and age of the last update. Rows appear when a path manager starts and disappear when its session ends. The panel polls the store version each frame; an unchanged version costs one atomic load.

## 10. System tray (Windows only)

On Windows the app creates one tray icon with a menu: Show, Connect, Disconnect, Quit. Closing the window minimizes to the tray instead of exiting; Quit is the only menu path that ends the process. Tray events reach the UI through a bounded `std::sync::mpsc` channel drained by a dedicated thread that calls `request_repaint`, keeping the eframe event loop unmodified. The module is `cfg(windows)`; other platforms compile inert stubs, and the event-decoding logic is unit-tested on all platforms.

## 11. Testing strategy

- Headless unit coverage: connection state transitions, tunnel projection, log ring bounds and drop-oldest behavior, telemetry ring bounds, P2P store ordering/version/insert-remove, tray event decoding, formatters.
- In-process integration (`tests/gui_state.rs`): a real `rustgos` `ServerApp` plus `ClientApp::with_runtime` with a deterministic short backoff drives the same view models the UI uses; scenarios cover connect, tunnel rows, traffic snapshots, forced relay fallback and promotion for the path store, disconnect, and fail-stop surfacing.
- `--selfcheck` exercises the shipped binary headless against a real server in both e2e scripts (Windows PowerShell and Linux shell), asserting exit 0 and expected log lines.
- Window rendering, tray interaction, and chart drawing are verified manually on Windows; Linux is verified by compiling, running the full headless suite, and a manual smoke run where a desktop is available.

## 12. Acceptance criteria

V0.4 is accepted only when all of the following are true:

1. `rustgoc-gui` connects to V0.1/V0.2/V0.3 servers through the unmodified `rustgoc` library and displays generation, tunnel rows, and accepted state that match the headless client's behavior for the same configuration.
2. Connect/disconnect start and join the client runtime without leaking tasks, sockets, or log lines; window close on Windows minimizes to tray and only Quit exits.
3. Traffic totals appear when client telemetry is enabled and the panel shows an explicit disabled note when it is not.
4. The P2P panel reflects relay fallback and direct promotion within one UI tick of the underlying transition, and removes rows when sessions end.
5. Telemetry charts retain at most 300 points per series and survive sampler errors without affecting connection state.
6. The log view shows at most 1,000 bounded lines and the ring drops oldest under flooding without unbounded memory.
7. `--selfcheck` exits 0 against a live server on both platforms and is wired into both e2e scripts.
8. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` pass on Windows and Linux, with `#![forbid(unsafe_code)]` preserved in every crate.
9. Linux builds contain no tray dependency and no GTK/appindicator linkage; Windows and Linux binaries interoperate with the existing server in the full e2e suites.
