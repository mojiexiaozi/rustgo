# Rustgo V0.2 P2P Design

## 1. Purpose and scope

V0.2 adds authenticated device-to-device connectivity to the V0.1 TCP and UDP relay. Two `rustgoc` devices establish an end-to-end encrypted session while `rustgos` supplies authentication, rendezvous, candidate exchange, and a reliable relay fallback. The path manager prefers QUIC over UDP, tries native TCP simultaneous-open when UDP is unavailable, and falls back to the existing relay when neither direct path succeeds.

V0.2 targets difficult consumer and enterprise NATs but does not promise universal direct connectivity. Symmetric NAT, CGNAT, and restrictive firewalls can make direct connectivity impossible; relay fallback is a required success path rather than an exceptional mode.

V0.2 excludes UPnP, NAT-PMP, PCP, a web administration interface, mobile background keepalive, TUN networking, virtual addressing, and routing.

## 2. Compatibility and deployment

The existing `rustgos` and `rustgoc` binaries remain the only deliverables. V0.1 `[[tunnels]]` configurations and relay behavior remain supported without migration. P2P is opt-in through new client configuration.

The server continues to use its fixed TLS control port, currently `7443/tcp` in the reference deployment. P2P discovery uses `7443/udp` and `7444/udp` on the same public IP. A second public observation address may be added later for more accurate RFC 5780 behavior discovery, but it is not required for V0.2.

Linux remains the primary server platform. Linux and Windows clients must interoperate. Protocol negotiation must allow a V0.2 server to reject unsupported P2P operations without breaking compatible V0.1 relay operations.

## 3. Architecture

Three focused workspace crates are added:

- `rustgo-rendezvous`: typed signaling messages, signed candidate sets, session coordination, expiration, and protocol state. It owns no sockets.
- `rustgo-nat`: local candidate collection, observation probes, mapping-behavior analysis, bounded UDP port prediction, and native TCP simultaneous-open.
- `rustgo-path`: candidate prioritization, concurrent connectivity checks, winner selection, health monitoring, relay fallback, and background direct-path rechecks.

Existing crates retain their boundaries:

- `rustgo-protocol` owns shared framing and version rules.
- `rustgo-crypto` owns device identity and end-to-end session key derivation.
- `rustgo-config` owns strict TOML parsing and semantic validation.
- `rustgo-transport` supplies the common stream/datagram abstraction plus QUIC, native TCP, and relay implementations.
- `rustgos` authenticates devices, enforces limits, coordinates rendezvous, and provides relay transport.
- `rustgoc` owns exports, forwards, local listeners, peer sessions, and reconnect lifecycle.

No NAT or path-selection logic is embedded directly in the executable crates. The rendezvous protocol is separate from the established V0.1 tunnel-registration messages even when both share the authenticated control connection.

## 4. Device and service model

Both peers run `rustgoc`. A provider declares named `[[exports]]`; a consumer declares local `[[forwards]]` that target a peer name and export name.

```toml
[client]
name = "office-pc"
server_addr = "8.133.176.172:7443"
server_name = "rustgo-server.local"
certificate_authority_file = "./ca.crt"
private_key_file = "./keys/device.key"

[p2p]
enabled = true
prefer_direct = true
direct_timeout_secs = 8
reconnect_timeout_secs = 3
allow_relay_fallback = true
udp_port_range = "7400-7499"
tcp_port_range = "7400-7499"

[[exports]]
name = "ssh"
protocol = "tcp"
local_addr = "127.0.0.1:22"
allowed_peers = ["laptop"]

[[exports]]
name = "game"
protocol = "udp"
local_addr = "127.0.0.1:27015"

[[forwards]]
name = "home-ssh"
peer = "home-pc"
export = "ssh"
listen_addr = "127.0.0.1:2222"
```

Names are unique within their respective collections. A forward must not target the local device. TCP forwards bind TCP listeners and UDP forwards bind UDP sockets. UDP forwarding preserves application datagram boundaries.

`allowed_peers` has these exact semantics:

- Missing `allowed_peers` permits every registered, enabled, successfully authenticated client on the same `rustgos`.
- `allowed_peers = []` has the same allow-all meaning.
- A non-empty list permits only the named registered and enabled clients.
- There is no deny-all shorthand in V0.2.

Configuration checking and startup emit a conspicuous warning for every allow-all export but do not reject it. An unregistered, disabled, or unauthenticated device is always denied. The provider enforces export authorization locally even if the rendezvous server has already admitted the session request.

Listening on loopback is the safe default demonstrated by examples. LAN or wildcard listening requires an explicit `listen_addr` and produces a warning. Unknown TOML fields remain errors.

## 5. Identity and end-to-end security

The V0.1 Ed25519 device identity remains authoritative. `rustgos` stores registered public keys and supplies the authenticated peer directory, so client TOML does not duplicate every peer public key. The peer public key returned for a session must match the identity already authenticated on the control connection.

Every rendezvous message contains a protocol version, random session identifier, sender and target identities, monotonic message step, expiration time, and Ed25519 signature over a canonical transcript. Expired messages, duplicate steps, replayed session identifiers, signature failures, and identity mismatches are rejected.

Each P2P attempt generates ephemeral key material. The end-to-end session key derivation binds both device public keys, both ephemeral keys, the rendezvous session identifier, requested export, negotiated protocol version, and transcript hash. QUIC and native TCP paths mutually authenticate this transcript before application traffic is accepted.

Relay fallback carries the same end-to-end encrypted session frames through `rustgos`; it does not revert to server-readable application payload. The server can observe identities, export names, candidate metadata, timing, sizes, and encrypted traffic, but cannot decrypt application bytes.

## 6. Candidate discovery and NAT behavior

Each peer gathers a bounded candidate set:

- IPv6 addresses with usable scope;
- local IPv4 interface addresses;
- server-observed UDP mappings from `7443/udp` and `7444/udp`;
- native TCP candidates bound inside the configured TCP port range;
- the authenticated relay candidate.

Candidates include transport, address, priority, foundation, generation, expiration, and observation source. Private addresses are exchanged because peers may share a LAN. Link-local and otherwise unusable addresses are filtered unless their required scope information can be represented safely.

Comparing mappings observed through two UDP destination ports on the same server IP provides useful but incomplete behavior evidence. Rustgo labels results as observations rather than claiming a definitive RFC NAT type when the evidence is insufficient.

For changing UDP mappings, `rustgo-nat` may test a small predicted port window derived from recent observations. The window, total candidates, concurrent checks, probe rate, and total discovery duration all have hard configuration-independent ceilings. Rustgo never performs an unbounded port scan.

Native TCP uses a pre-bound local port and simultaneous-open attempts against signed peer candidates. TCP hole punching is a secondary path used when the preferred QUIC/UDP route does not succeed.

## 7. Rendezvous and path selection

A forward connection follows this sequence:

1. The consumer asks `rustgos` for a session with a named peer and export.
2. `rustgos` verifies that both identities are registered, enabled, authenticated, online, and within session limits.
3. The provider performs the authoritative local `allowed_peers` check and accepts or rejects the export request.
4. Both peers gather candidates and exchange signed candidate sets plus ephemeral session parameters through `rustgos`.
5. The path manager races viable candidates in priority groups: IPv6 direct, QUIC/UDP direct, native TCP direct, then relay.
6. Relay starts after a short bounded delay rather than waiting for the entire direct timeout, keeping connection setup predictable on hostile networks.
7. The first path that completes connectivity checks and mutual end-to-end authentication becomes primary. All losing attempts and their sockets are cancelled and released.

The path state machine is:

```text
Discovering -> Checking -> Direct
                      \-> Relay
Direct/Relay -> Rechecking -> Direct/Relay
Direct/Relay/Rechecking -> Closed
```

An illegal transition is an internal protocol error and closes only the affected peer session. Direct failure is a normal network outcome, not a process error.

The primary path carries reliable streams for TCP exports and boundary-preserving datagrams for UDP exports. QUIC streams carry TCP application connections; QUIC datagrams carry UDP application datagrams. If UDP is blocked, native TCP supplies the encrypted reliable transport. UDP exports cannot silently switch to stream semantics; when no datagram-capable direct path exists they use the datagram-preserving relay.

## 8. Health, migration, and fallback

Every selected path has bounded liveness checks. A failed direct path gets a short reconnect window of `reconnect_timeout_secs`. If it cannot recover, traffic switches to the prepared relay path. During relay operation, low-rate background checks may promote a newly working direct path after mutual confirmation.

Network-interface or observed-mapping changes invalidate the affected candidate generation and trigger fresh discovery. Old candidates and late packets cannot attach to a newer generation. Path promotion or demotion must preserve individual TCP connection ordering; an existing byte stream is either migrated by a transport that guarantees ordering or cleanly re-established according to its local connection semantics. V0.2 does not promise transparent survival of every established native TCP application connection across path failure.

UDP sessions may move between datagram-capable paths using generation and sequence metadata for duplicate suppression. Application payloads are never logged during migration.

## 9. Limits and failure isolation

Hard limits cover concurrent rendezvous sessions per device, candidates per session, simultaneous checks, prediction-window size, probe rate, handshake bytes, queued streams, queued datagrams, idle peer sessions, and background rechecks. Server and client limits apply before allocation based on untrusted lengths.

Failure of one candidate, export, forward, stream, datagram session, or peer path does not terminate unrelated work. A provider going offline rejects new forwards and closes only its peer sessions. Loss of the server control connection prevents new rendezvous but does not immediately destroy an already authenticated direct session; relay sessions necessarily fail and reconnect through the normal control lifecycle.

All spawned tasks and sockets are owned by a session cancellation tree. Session close, configuration rejection, process shutdown, and losing a candidate race release owned resources within bounded time.

## 10. Logging and diagnostics

Logs remain human-readable, single-line text; JSON logging is not added. Stable event names cover discovery start/result, candidate check, direct selection, TCP selection, relay fallback, path loss, recheck, promotion, authorization rejection, and cleanup.

Candidate endpoints, device names, export names, short fingerprints, session IDs, and failure categories may be logged. Private keys, ephemeral secrets, full signatures, canonical transcripts, and application payloads never appear. Repeated network failures and probe rejections are rate-limited.

Allow-all exports produce a warning during `check` and startup. Relay fallback is logged at `info` when it is an ordinary reachability result; authentication or transcript failures use `warn` or `error` according to whether the process can continue.

## 11. Testing strategy

Unit tests cover strict TOML parsing, allow-all semantics for missing and empty `allowed_peers`, named allowlists, candidate ordering, observation interpretation, prediction bounds, rendezvous state, transcript binding, expiration, replay rejection, path transitions, timeout behavior, and cancellation.

Property and fuzz tests cover rendezvous frames, signed candidate sets, malformed addresses, oversized collections, duplicate candidates, invalid state ordering, and arbitrary untrusted input.

Linux network-namespace integration tests create deterministic topologies representing endpoint-independent mapping, address-dependent filtering, port-dependent filtering, symmetric mapping behavior, shared LAN, IPv6 direct connectivity, UDP blocking, and total direct-path failure. Tests assert the selected path and cleanup, not just payload delivery.

Real-process E2E tests launch one `rustgos`, two `rustgoc` processes, and TCP/UDP echo services. They verify:

- QUIC streams for TCP exports;
- QUIC datagrams for UDP exports;
- native TCP simultaneous-open when UDP is blocked;
- datagram-preserving relay when direct UDP cannot work;
- automatic relay fallback within a bounded setup time;
- direct-path re-promotion after reachability returns;
- provider-side authorization and allow-all warnings;
- server restart, client reconnect, network changes, and bounded cleanup;
- Linux/Windows interoperability.

Remote acceptance uses `8.133.176.172` without disturbing the existing `frps` listener. It validates `7443/tcp`, `7443/udp`, and `7444/udp`, device authentication, TCP and UDP application traffic, a proven direct path where the endpoint networks permit it, and a deliberately forced relay fallback. Existing V0.1 TCP and UDP relay tests remain release gates.

## 12. Acceptance criteria

V0.2 is complete only when:

1. Two authenticated `rustgoc` devices can consume authorized named TCP and UDP exports.
2. QUIC/UDP is preferred, native TCP direct is attempted when UDP is unavailable, and the existing relay is used when direct connectivity fails.
3. Relay application traffic remains end-to-end encrypted between devices.
4. Missing or empty `allowed_peers` permits all registered and enabled clients and emits a warning; a non-empty list is enforced locally by the provider.
5. Signed rendezvous transcripts reject expiration, replay, identity substitution, export substitution, and candidate tampering.
6. Complex-NAT prediction and connectivity checks have tested hard bounds and cannot become an unbounded scanner.
7. TCP streams and UDP datagrams retain their required semantics on every selected path.
8. Network change, path loss, fallback, recheck, and cleanup pass real-process and namespace tests without unbounded task, socket, queue, or memory growth.
9. V0.1 configuration and relay behavior remain compatible and pass their existing release gates.
10. Linux and Windows clients interoperate with the Linux server, and operator documentation explains required TCP/UDP firewall ports and the limits of NAT traversal.
