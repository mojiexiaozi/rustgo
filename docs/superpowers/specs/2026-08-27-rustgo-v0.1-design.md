# Rustgo V0.1 Design

## 1. Purpose and scope

Rustgo is a long-lived, high-performance, low-resource network tunneling tool written in Rust. It is intended first for personal self-hosting: one public server serves multiple explicitly authorized private-network clients.

V0.1 establishes a reliable relay baseline. It supports fixed-port TCP and UDP forwarding, TLS 1.3, per-device authentication, bounded resource usage, and automatic reconnection. All V0.1 application traffic passes through the public server. NAT discovery, hole punching, direct P2P transport, virtual networking, multi-tenancy, billing, and a web administration interface are outside V0.1. P2P is planned for V0.2 and must be able to fall back to the V0.1 relay path.

## 2. Deliverables

The project produces two independent executables:

- `rustgos`: public relay server.
- `rustgoc`: private-network client.

Both target Linux and Windows. Linux is the primary server platform; clients on both platforms must interoperate.

The default invocation omits a `run` subcommand. Running either executable with no arguments is exactly equivalent to passing its conventional configuration filename with `-c`:

```text
rustgos              == rustgos -c server.toml
rustgoc              == rustgoc -c client.toml
```

An explicit `-c`/`--config` always selects that path instead of the conventional filename:

```text
rustgos -c production-server.toml
rustgoc -c laptop-client.toml
```

Explicit utility commands are:

```text
rustgos check -c server.toml
rustgoc check -c client.toml
rustgoc keygen -o ./keys
```

When `-c`/`--config` is absent, `rustgos` uses `./server.toml` and `rustgoc` uses `./client.toml`. These paths are resolved from the current directory. A missing file is an error with a concise message that states the attempted path and shows how to pass `-c`; the programs do not search parent or platform-specific configuration directories and do not silently generate configuration or credentials.

## 3. Workspace architecture

Rustgo uses a modular Cargo workspace:

```text
rustgo/
├── Cargo.toml
├── crates/
│   ├── rustgo-protocol/
│   ├── rustgo-crypto/
│   ├── rustgo-config/
│   ├── rustgo-transport/
│   ├── rustgos/
│   └── rustgoc/
└── docs/
```

Responsibilities are:

- `rustgo-protocol`: wire messages, framing, version negotiation, protocol state rules, and typed errors. It does not own sockets or depend on Tokio networking types.
- `rustgo-crypto`: device key generation/loading, public-key fingerprints, challenge signing, and signature verification.
- `rustgo-config`: TOML parsing, environment substitution, path resolution, and semantic validation shared by runtime and `check`.
- `rustgo-transport`: interfaces for control and data channels plus the V0.1 TLS relay implementation. Its interfaces permit later QUIC relay and QUIC P2P implementations.
- `rustgos`: public listeners, client authentication, tunnel registration, limits, and relay lifecycle.
- `rustgoc`: local-service connections, server session lifecycle, tunnel registration, and reconnect behavior.

Shared crates never depend on either executable crate. The server does not contain a client runtime mode, and the client does not contain a server runtime mode.

## 4. Configuration contract

TOML is the only supported configuration format. Unknown fields are rejected. Relative paths are resolved against the directory containing the configuration file, not the process working directory. Explicit `${VARIABLE_NAME}` substitutions are allowed; an absent variable is an error. Secret values must never appear in logs or formatted errors.

Example server configuration:

```toml
[server]
bind_addr = "0.0.0.0:7000"
certificate_file = "./certs/server.crt"
private_key_file = "./certs/server.key"
heartbeat_timeout_secs = 60

[limits]
max_clients = 128
max_tunnels_per_client = 64
max_tcp_connections_per_tunnel = 256
max_udp_sessions_per_tunnel = 1024
max_udp_payload_bytes = 65507

[[clients]]
name = "home-pc"
public_key = "ed25519:BASE64_PUBLIC_KEY"
enabled = true
```

Example client configuration:

```toml
[client]
name = "home-pc"
server_addr = "tunnel.example.com:7000"
server_name = "tunnel.example.com"
private_key_file = "./keys/device.key"
heartbeat_interval_secs = 20

[[tunnels]]
name = "ssh"
protocol = "tcp"
local_addr = "127.0.0.1:22"
remote_port = 2222

[[tunnels]]
name = "game"
protocol = "udp"
local_addr = "127.0.0.1:27015"
remote_port = 27015
```

Client names, tunnel names within a client, and remote ports within the same transport protocol must be unique. Ports, timeouts, payload limits, queue capacities, and connection limits are range-checked before runtime startup. `check` uses the same parser and semantic validator as `run`; it checks referenced file existence and key formats but neither binds sockets nor contacts a server. Configuration changes require a restart in V0.1.

## 5. Identity and transport security

All production control and relay connections require TLS 1.3. There is no plaintext configuration mode. A development-only insecure option, if later needed for local tests, must not be accepted from production TOML.

Every client has an independent Ed25519 device key pair. Its private key remains on the client and is referenced by file; the server stores only the authorized public key. The human-readable client name is an alias, not an authenticator. The configured name and public key must both match one enabled server authorization entry.

Authentication proceeds as follows:

1. `rustgoc` opens TLS and validates the server certificate and configured server name.
2. `rustgoc` sends the protocol version, client name, and public-key fingerprint.
3. `rustgos` returns a cryptographically random challenge and server session ID.
4. `rustgoc` signs a canonical transcript containing the challenge, session ID, negotiated protocol version, and client name.
5. `rustgoc` sends its public key, signature, and requested tunnels.
6. `rustgos` verifies the signature, name-to-key binding, enabled status, protocol state, and tunnel authorization constraints before registering listeners.

The random challenge prevents transcript replay. A repeated client name with another key and a repeated key with another name are rejected. When an already connected identity logs in again, the later connection is rejected; an incoming connection cannot evict the established session.

## 6. Connection model

Control and application data use separate TLS connections.

Each client maintains one long-lived control connection for authentication, tunnel registration, results, heartbeat, and lifecycle commands. Control traffic never carries application payload. A disconnect stops new traffic for that client, releases its public listeners, and closes its established data sessions so the system has one unambiguous ownership state.

The client reconnects using capped exponential backoff with random jitter. After successful authentication it re-registers its complete configured tunnel set. The server does not retain listener ownership for disconnected clients.

### 6.1 TCP forwarding

For each accepted public TCP connection:

1. `rustgos` allocates a bounded connection ID and notifies `rustgoc` through the control channel.
2. `rustgoc` opens a separate authenticated TLS data connection that identifies the connection ID.
3. `rustgoc` connects to the configured local TCP target.
4. After both sides report readiness, the endpoints copy bytes bidirectionally, preserving TCP half-close behavior.

A failure closes only that session. It does not terminate the control connection or unrelated tunnels. Independent data connections avoid TCP head-of-line blocking between application sessions.

### 6.2 UDP forwarding

UDP datagram boundaries are preserved. The server identifies a temporary flow by tunnel plus external source address and the relevant public destination. It assigns a bounded session ID and transports datagrams for the tunnel over a persistent TLS data channel. Each application frame contains the session ID, required address metadata, payload length, and unchanged UDP payload.

UDP sessions expire after a configured idle timeout. Session tables, outbound queues, frame sizes, and per-tunnel session counts have hard limits. When a bounded UDP queue is full, the datagram is dropped and the event is counted and logged at an appropriate rate-limited level; memory usage must not grow without limit.

## 7. Wire protocol and evolution

Control messages use a length-prefixed binary frame:

```text
magic | protocol_version | message_type | flags | payload_length | payload
```

Multibyte integers use network byte order. Message identifiers are explicit stable numeric values and never depend on Rust enum layout. Structured payloads use `postcard` with Serde in V0.1. Raw application bytes are framed without encoding them as JSON or another textual representation.

Initial message families include:

```text
ClientHello
ServerChallenge
ClientAuthenticate
AuthResult
RegisterTunnels
TunnelResults
OpenTcpStream
TcpStreamReady
UdpDatagram
Heartbeat
Error
```

The handshake negotiates major and minor protocol versions. An unsupported major version is rejected with a stable protocol error. Unknown messages, oversized lengths, truncated payloads, invalid enum values, and illegal state transitions are rejected without allocating from untrusted lengths. Depending on scope, the corresponding data connection or entire unauthenticated/control session is then closed.

The logical tunnel/session API is independent of transport. V0.1 implements TLS relay transport. V0.2 may add QUIC relay and QUIC P2P transports while retaining identity, tunnel definitions, error semantics, and the reliable relay fallback.

## 8. Error isolation and limits

- An invalid or unavailable tunnel is rejected individually; other valid tunnels continue running.
- Authentication failure closes the device session and registers no listeners.
- Public port conflicts reject the affected tunnel with an explicit error.
- A TCP session failure closes only that connection.
- Control loss removes the client's public listeners and active data sessions.
- UDP overload drops bounded work rather than expanding memory indefinitely.
- Frame length, connection count, tunnel count, UDP payload, session table, queues, authentication attempts, and relevant timeouts all have explicit hard limits.
- Listener registration and release are owned by the authenticated control-session lifecycle, preventing stale ownership.

## 9. Logging and diagnostics

V0.1 emits only human-readable, single-line text logs. JSON log output is not supported. A representative line is:

```text
2026-08-27T14:32:10.125+08:00 INFO client=home-pc tunnel=ssh conn=a31f event=tcp_open peer=203.0.113.8:53120
```

Timestamps use ISO 8601 with an offset. Supported levels are `error`, `warn`, `info`, `debug`, and `trace`; the default is `info`, configurable through TOML or `RUST_LOG`. Stable-looking `key=value` context improves human diagnosis but the text format is not a promised machine interface. Future automation should use a metrics or status interface rather than parsing logs.

Routine startup, authentication, registration, and reconnection events use `info`. Recoverable session faults normally use `warn`; `error` is reserved for conditions that prevent the process or a required subsystem from continuing. Logs may contain client names, tunnel names, short public-key fingerprints, connection IDs, and network endpoints. They never contain private keys, full signatures, challenge material, or application payloads.

V0.1 has no web administration UI. A status endpoint or local status command is not required for V0.1 acceptance.

## 10. Testing strategy

Unit tests cover configuration parsing and validation, path resolution, environment substitution, frame codecs, device signatures, authentication transcripts, protocol state machines, limits, and reconnect backoff.

Property and fuzz tests cover oversized lengths, unknown message IDs, truncation, malformed payloads, illegal state ordering, and arbitrary untrusted frame input.

Process-level integration tests launch a real `rustgos`, `rustgoc`, and local echo services. They exercise actual sockets and process lifecycle rather than only mocked callbacks.

TCP tests cover concurrent sessions, bidirectional transfer, large transfers, slow consumers, half-close behavior, isolated failures, server restart, and listener recovery. UDP tests cover datagram-boundary preservation, multiple external sources, replies, idle cleanup, queue overflow, and session limits.

Security tests verify rejection of unknown keys, mismatched names and keys, disabled devices, duplicate login, replayed signatures, invalid signatures, invalid server certificates, unsupported versions, and attempts to exceed configured limits.

Stability tests repeatedly disconnect and reconnect clients and run sustained traffic while checking that tasks, sockets, session-table entries, and memory usage do not grow without bound. Cross-platform tests verify Windows/Linux client interoperability against the primary Linux server target.

## 11. V0.1 acceptance criteria

V0.1 is complete only when:

1. Fixed-port TCP and UDP mappings pass real multi-process end-to-end tests.
2. TLS server verification and per-device challenge signatures cannot be bypassed in production configuration.
3. Client name and public-key authorization bindings, duplicate-login behavior, and disabled-client behavior match this design.
4. One failed tunnel or data session does not terminate unrelated tunnels.
5. A server restart causes the client to reconnect automatically and restore its valid mappings.
6. Frames, queues, connections, tunnels, authentication attempts, and UDP sessions have tested hard bounds.
7. Windows and Linux release artifacts for `rustgos` and `rustgoc`, example TOML files, and operator documentation are produced.
8. Documentation clearly states that V0.1 is relay-only and that P2P is a V0.2 capability with relay fallback.

## 12. Deferred work

V0.2 will design NAT classification, endpoint exchange, UDP hole punching, encrypted QUIC P2P sessions, path selection, keepalive behavior, migration, and automatic relay fallback. A later independent phase may add TUN-based virtual networking, virtual addressing, routes, DNS, and access-control policy. These features must not be partially implemented inside V0.1.
