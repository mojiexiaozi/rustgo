# Rustgo V0.3 Web Dashboard Design

## 1. Purpose and scope

V0.3 adds an embedded, read-only operations dashboard to `rustgos`. The dashboard makes a personal Rustgo deployment observable without introducing a second daemon, a database server, a web administration plane, or machine-parsed logs. It shows server resources, authenticated client health, exports and forwards, P2P path selection, relay use, active sessions, traffic rates, failures, and bounded historical trends.

V0.3 also adds lightweight host telemetry to `rustgoc`. Client telemetry travels over the existing mutually authenticated control connection and is always bound to the authenticated client identity. V0.2 clients remain compatible; they appear in the dashboard with connection and Rustgo traffic state but without host-resource fields.

The dashboard is strictly read-only. V0.3 does not provide configuration editing, process restart, client disconnect, key rotation, command execution, file browsing, a public management API, multi-user roles, alert delivery, Prometheus export, or multi-server clustering. These exclusions keep the first management surface small enough to secure and operate confidently.

## 2. Compatibility and defaults

The existing `rustgos` and `rustgoc` binaries remain the only runtime deliverables. Missing `[web]` and `[telemetry]` sections preserve V0.2 behavior and do not open a new listener or send host telemetry. V0.1 tunnel mappings and V0.2 P2P behavior remain supported.

The dashboard uses a separate HTTP listener and never shares `7443/tcp`, `7443/udp`, or `7444/udp`. The default reference address is `127.0.0.1:7450`. `rustgos check` and startup reject a non-loopback Web bind. Remote access is provided by an operator-managed HTTPS reverse proxy such as Caddy or Nginx.

Logs remain human-readable single-line text. The dashboard API uses bounded JSON responses; this does not add JSON logging or make log text a stable automation interface.

## 3. Architecture and ownership

A new workspace crate, `rustgo-observability`, owns shared telemetry types, immutable snapshots, aggregation, retention, and SQLite persistence. It has no dependency on Axum, Rustgo sockets, control-session ownership, or P2P path ownership.

`rustgos` adds four isolated components:

- a server host sampler;
- an authenticated client-telemetry receiver;
- an event-to-snapshot aggregator and bounded SQLite writer;
- a read-only HTTP service serving API responses and embedded static assets.

Core server modules publish immutable, redacted observations through narrow interfaces. The dashboard cannot acquire mutable registry entries, cancellation tokens, peer path handles, control writers, listeners, or sockets. The Web module can query a snapshot or history store but cannot change Rustgo runtime state.

`rustgoc` adds a host sampler and a low-priority telemetry publisher. The publisher uses the current authenticated control generation. It does not start another network connection and cannot delay authentication, heartbeat frames, rendezvous messages, or tunnel data.

The frontend is checked-in HTML, CSS, and small vanilla JavaScript modules embedded into `rustgos`. It uses browser-native SVG or Canvas charts and has no Node.js runtime or external CDN dependency. Release builds therefore remain a single executable plus TOML, keys, certificates, and the SQLite file created at runtime.

## 4. Failure isolation and resource bounds

Observability is subordinate to the data plane:

- Runtime producers use atomic counters, immutable snapshots, or bounded `try_send`; they never await SQLite or HTTP work.
- The SQLite writer owns one bounded queue with a hard capacity of 1,024 batches. A full queue drops the oldest pending historical batch, increments a visible loss counter, and preserves the latest real-time snapshot.
- HTTP concurrency, login attempts, response bytes, query duration, history range, returned points, and open request bodies all have configuration-independent ceilings.
- Sampler, writer, retention, and Web tasks are owned by the application shutdown tree and are joined before process exit.
- A database error, full disk, slow query, corrupt history database, or Web listener failure cannot stop TCP, UDP, QUIC, native TCP, relay, authentication, or heartbeats.

If the configured Web listener cannot bind, startup fails because the requested operator surface is unavailable. If SQLite cannot open or later becomes unavailable, startup or runtime continues with live in-memory state and a prominent `history_unavailable` warning in logs and the dashboard. This degraded behavior is explicit and bounded.

## 5. Configuration

Server configuration adds:

```toml
[web]
enabled = true
bind = "127.0.0.1:7450"
admin_username = "admin"
admin_password = "replace-with-at-least-16-characters"
cookie_secure = true
history_days = 7
database_path = "./rustgo-metrics.db"
database_max_mib = 256
```

Client configuration adds:

```toml
[telemetry]
enabled = true
sample_interval_secs = 10
report_interval_secs = 30
```

Exact rules:

- `[web]` is optional and defaults to disabled.
- `bind` must resolve to a loopback IPv4 or IPv6 address and a nonzero port.
- The username is configurable, contains 1 to 64 printable non-control UTF-8 bytes, and is compared exactly.
- The plaintext password is intentionally stored in TOML at the user's request. It must contain at least 16 and at most 256 UTF-8 bytes.
- Passwords are never returned by Debug, validation, error, log, API, or diagnostic output.
- On Unix, enabling Web requires the configuration file not to be readable by group or other users. On Windows, `check` and startup emit an explicit ACL review warning because portable exact ACL interpretation is not reliable.
- `cookie_secure = true` is required for reverse-proxied HTTPS. It may be false only because the listener is loopback-only, enabling direct local HTTP use.
- `history_days` is bounded from 1 to 30.
- `database_max_mib` is bounded from 16 to 4,096.
- The database path resolves relative to the configuration directory and must not be the configuration file, key file, certificate, directory, or special device.
- Client sampling is bounded from 5 to 300 seconds. Reporting is bounded from 10 to 600 seconds and cannot be faster than sampling.

`rustgos check` performs all static validation without binding the Web port or opening the database for mutation. Examples use environment substitution for secrets and never contain a usable password.

## 6. Metrics and snapshots

The server sampler runs every two seconds and records:

- total host CPU and `rustgos` process CPU;
- host used/total memory and `rustgos` resident memory;
- capacity, free space, read rate, and write rate for the filesystem containing the database and configured Rustgo files;
- aggregate network receive and transmit rates from bounded interface counters;
- Rustgo logical TCP, UDP, QUIC, native TCP, and relay bytes;
- authenticated clients, control connections, rendezvous sessions, P2P sessions, active relays, exports, forwards, queue occupancy, drops, authentication failures, reconnects, path losses, and promotions.

Each client samples every ten seconds and reports every thirty seconds by default:

- total host and `rustgoc` process CPU;
- host used/total memory and `rustgoc` resident memory;
- bounded filesystem capacity/free values and read/write rates;
- aggregate host network receive/transmit rates;
- Rustgo logical upload/download totals and rates;
- version, process uptime, exports, forwards, active TCP/UDP flows, selected path counts, reconnect count, and latest path transition reason.

Counters use saturating arithmetic and explicit reset detection. Interface removal, counter wrap, reboot, sleep/resume, or a clock jump starts a new baseline instead of producing a negative rate or spike. Reports use monotonic sample ages plus a server receipt timestamp; client wall-clock time is informational and cannot control retention.

Collections have hard bounds: at most 16 filesystems, 16 network interfaces, 256 exports, 256 forwards, and protocol-defined limits on counters and labels. Paths, mount names, interface descriptions, command lines, environment variables, hostnames, usernames, and application payloads are not transmitted unless already part of the authenticated Rustgo device model.

## 7. Telemetry protocol and identity

V0.3 appends bounded telemetry messages to `rustgo-protocol` without renumbering or reinterpreting V0.1/V0.2 message IDs. Protocol negotiation makes telemetry optional. A V0.2 peer ignores the unavailable capability and continues normal tunnel and P2P operation.

A telemetry report contains a schema version, monotonically increasing report sequence, sample age, bounded host-resource values, bounded Rustgo counters, and a flags field for unavailable measurements. It does not carry the client name as authority. `rustgos` assigns the report to the name and device key of the authenticated control session.

The server rejects oversized, malformed, duplicate, stale, too-frequent, wrong-version, or non-finite values before allocation or persistence. One client can have at most one accepted report per configured report interval, with a small bounded jitter allowance. Invalid telemetry increments a bounded diagnostic counter but does not disclose validation detail to unauthenticated peers.

Telemetry is a low-priority business frame. Existing heartbeat, authentication, close, rendezvous, and data-plane admission remain higher priority. Control backpressure drops telemetry rather than delaying liveness or protocol work.

## 8. SQLite history and retention

SQLite is embedded through a Rust library and runs in WAL mode with one writer task. SQL is parameterized; the Web API never accepts raw SQL, column names, or sort expressions.

The database contains versioned migrations and these logical records:

- server metric buckets;
- client metric buckets keyed by authenticated client identity;
- bounded path/session lifecycle summaries;
- observability health and dropped-sample counters.

Raw or fine-grained server samples are retained for one hour. Data from one to twenty-four hours is aggregated into one-minute buckets. Data from one day through the configured retention horizon is aggregated into five-minute buckets. Client reports use their native report cadence for one hour and the same later aggregation tiers. A retention task runs every ten minutes and performs bounded work per pass.

The default database cap is 256 MiB and accounts for the main database, WAL, and shared-memory sidecar files together. When the cap is approached, the writer first compacts eligible old buckets, then deletes the oldest completed buckets until it reaches a lower watermark. Active transactions, current snapshots, credentials, configuration, and runtime state are never deleted. Database maintenance has a hard time budget and yields between batches.

Corrupt or incompatible history is moved aside to a timestamped quarantine path only after the exact path is validated as the configured database file. Rustgo starts a fresh database and reports the quarantine. It never recursively deletes or overwrites an arbitrary directory.

## 9. Authentication and HTTP security

The dashboard has one configured administrator account. Login hashes the supplied and configured exact UTF-8 byte strings into fixed-size comparison values and compares both username and password values in constant time; neither value is normalized. Failure timing does not reveal whether the username or password differed.

Successful login creates a cryptographically random opaque session ID. Only an HMAC-protected session value is stored in the cookie; the process keeps a bounded in-memory session table. The signing key is generated with the operating system RNG on every `rustgos` start, so all Web sessions expire after restart.

Sessions expire after 30 minutes of inactivity and eight hours absolutely. The session table is capped at 32 entries. Login failures are limited per canonical source and globally before expensive work. Bodies, headers, cookies, usernames, and passwords have hard length limits.

Cookies are `HttpOnly`, `SameSite=Strict`, scoped to the dashboard root, and use `Secure` when configured. Login and logout validate `Origin` against the configured host policy. The read-only API accepts only `GET` and `HEAD`; login/logout are the only state-changing HTTP routes and reject cross-origin form submissions.

Every response sets a restrictive Content Security Policy, `X-Content-Type-Options: nosniff`, frame denial, a strict referrer policy, and no-store caching on authenticated pages and APIs. Static assets use content hashes and may be cached. Directory listing, source maps containing local paths, stack traces, SQL errors, and internal filesystem paths are never served.

Proxy headers are not trusted in V0.3. Rate limiting uses the direct socket peer. Operators exposing the loopback listener through a reverse proxy therefore share one login rate bucket, which is safe and documented.

`/healthz` is unauthenticated and returns only process liveness with no version, client, metric, path, database, or configuration detail. Every other API and page requires a valid administrator session.

## 10. Read-only HTTP API

The versioned API is:

- `GET /api/v1/overview`
- `GET /api/v1/server/metrics`
- `GET /api/v1/clients`
- `GET /api/v1/clients/{name}`
- `GET /api/v1/sessions`
- `GET /api/v1/history`
- `GET /healthz`

Every endpoint has a fixed response schema, bounded arrays, escaped strings, and a maximum encoded response size. Client names use a percent-decoded single path segment and the same canonical validation as configuration; traversal and ambiguous encodings are rejected.

History accepts only enumerated metric names, an exact client identity where applicable, a bounded start/end range, and a point limit no greater than 2,000. The server chooses the aggregation tier. Query execution has a five-second hard deadline and cannot block the writer or runtime snapshot.

The UI polls the live overview and selected detail every two seconds. History is queried only when a page or time range changes. V0.3 does not add WebSockets or server-sent events.

## 11. Dashboard pages

The dashboard supports dark and light color schemes, is desktop-first, and remains usable on a phone. It uses restrained animation and does not require a third-party font or external asset.

The overview page contains:

- service health, version, uptime, observability degradation, online clients, and active alerts;
- CPU, memory, storage, upload, and download resource cards;
- CPU/memory, network, and Rustgo TCP/UDP/relay trend charts for one hour, twenty-four hours, and seven days;
- a searchable and sortable client-card grid.

Each client card shows:

- name, online/offline state, version, and last heartbeat;
- CPU, memory, and storage use with measurement age;
- live upload/download rate and cumulative logical traffic;
- export, forward, active TCP, and active UDP counts;
- primary path kind (`QuicV4`, `QuicV6`, `NativeTcp`, or `Relay`);
- badges for authentication failures, reconnects, path degradation, stale telemetry, and unavailable metrics.

Cards sort by online state then name by default. The operator can search by exact or substring client name and sort by online state, name, traffic, or CPU. Desktop layouts show three or four cards per row; narrow screens show one.

The client detail page shows resource trends, exports, forwards, current and recent P2P sessions, path-use counts, direct success rate, relay use, path changes, authentication failures, reconnects, limits, and degradation events.

The sessions page filters by client, protocol, path, and state. It shows only a shortened session identifier, authenticated peers, export, protocol, path, byte counts, start time, duration, and terminal reason. It never shows full session IDs, keys, tokens, full fingerprints, full public candidates, packet contents, application payloads, or raw control messages.

Offline clients remain visible with their last receipt timestamp and historical charts. Stale data is visually distinct and cannot appear live.

## 12. Diagnostics and privacy

Stable text event names cover Web start/stop, login success/failure, telemetry acceptance/rejection categories, sampler resets, writer queue loss, database degradation/recovery, retention, and query limits. Sensitive inputs are escaped and redacted before logging.

The dashboard itself exposes aggregate failure categories, not raw authentication transcripts or cryptographic errors. Client and session detail is available only after administrator authentication.

Metrics are operational data and can reveal device activity. Documentation instructs operators to protect the TOML and SQLite database, use HTTPS at the reverse proxy, restrict proxy access, back up only when required, and securely remove retired history files.

## 13. Testing strategy

Repository guidance favors functional tests and defers execution until an implementation unit is ready for acceptance. V0.3 tests exercise public behavior rather than private helper functions wherever practical.

Required functional coverage includes:

- real `rustgos` plus multiple `rustgoc` processes producing server and client resource snapshots;
- client cards, sorting, search, stale/offline display, detail views, sessions, and history ranges through a browser-facing HTTP contract;
- TCP, UDP, QUIC, native TCP, and relay traffic attributed to the correct authenticated clients and sessions;
- V0.2 clients connecting without telemetry and remaining fully functional;
- login, logout, expiry, rate limits, cookies, origin checks, response headers, loopback-only bind, secret redaction, and bounded requests;
- SQLite restart recovery, migrations, WAL behavior, tiered aggregation, retention, size cleanup, corruption quarantine, and disk-full degradation;
- invalid, duplicate, stale, oversized, high-rate, wrong-version, and identity-spoofed telemetry;
- Windows and Linux clients reporting to the primary Linux server;
- dashboard polling and history queries during sustained TCP/UDP/P2P load, proving no data-plane latency or liveness dependency;
- process shutdown proving samplers, database tasks, Web sockets, SQLite files, and temporary artifacts are released;
- release archives proving embedded assets are present and Linux scripts remain LF.

Final acceptance runs formatting, Clippy, the full Windows functional suite, locked release builds, Windows process E2E, Linux process E2E, Linux complex-NAT namespace regression, clean-up audits, mixed-OS telemetry, and deployment verification on the existing server while preserving `frps`.

## 14. Acceptance criteria

V0.3 is accepted only when all of the following are true:

1. Enabling Web creates one loopback-only read-only dashboard listener; disabling or omitting Web creates none.
2. The dashboard requires the configured administrator credentials and leaks neither password nor authenticated data through logs, errors, caches, health checks, or unauthenticated routes.
3. Server CPU, memory, storage, disk rate, host network rate, Rustgo logical traffic, and core runtime counts are visible live and historically.
4. Authenticated V0.3 clients report bounded resource and Rustgo state; V0.2 clients continue working and display telemetry as unavailable.
5. Client cards support search and the agreed sorting fields and link to correct details.
6. TCP, UDP, QUIC, native TCP, and relay activity is attributed to the correct device/session without exposing sensitive identifiers or payloads.
7. SQLite retains and aggregates seven days by default, respects its size ceiling, survives restart, and degrades without blocking the data plane.
8. Sampling, reporting, storage, HTTP, authentication, and query work remain bounded under hostile or overloaded input.
9. Web, telemetry, and database failure tests demonstrate that tunnel, P2P, relay, control heartbeat, and reconnect functions continue.
10. Windows/Linux functional, process, namespace, release, and deployed-server gates pass with no owned residue, and the unrelated `frps` service remains unchanged.
