# Rustgo V0.3 Web Dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an optional, read-only Web dashboard to `rustgos` that displays server and authenticated-client resource/traffic state, stores bounded local history in SQLite, and receives optional client telemetry without weakening V0.2 relay or P2P behavior.

**Architecture:** Add a shared `rustgo-observability` crate for normalized metrics, snapshots, bounded event queues, sampling, and SQLite persistence. `rustgoc` samples locally and sends a low-priority `TelemetryReport` over the authenticated control session. `rustgos` attributes reports to the authenticated session, combines them with server/runtime counters, persists aggregates, and serves an embedded HTML/CSS/JavaScript dashboard through a loopback-only Axum listener with built-in single-admin authentication.

**Tech Stack:** Rust 2024, Tokio, existing postcard protocol, Axum, serde/serde_json, sysinfo, rusqlite with bundled SQLite, HMAC/SHA-256, embedded static assets, vanilla JavaScript and SVG/Canvas.

**Spec:** `docs/superpowers/specs/2026-09-01-rustgo-v0.3-web-dashboard-design.md`

## Global Constraints

- Preserve `#![forbid(unsafe_code)]`, human-readable logs, default `rustgos -c server.toml` / `rustgoc -c client.toml`, fixed relay ports, per-device keys, and all V0.2 TCP/UDP/P2P behavior.
- Missing `[web]` disables Web and SQLite completely. Missing `[telemetry]` enables the documented client defaults only after V0.3 negotiation; a V0.2 peer must continue normally without telemetry.
- Web binds only to an IP loopback address. It is never exposed directly, never shares port 7443, and offers no mutation API.
- Metrics, database, and Web queues are bounded. Full queues drop/coalesce observability work; they never block heartbeat, relay, rendezvous, or shutdown.
- Never expose keys, passwords, full session IDs, candidate addresses, packet payloads, or raw control messages.
- Follow repository testing policy: implement each task without intermediate test runs; add functional/process coverage where practical; run the named concentrated verification only at the task's final checkpoint. Run the complete acceptance matrix after all tasks.
- Commit only scoped files after each task; do not merge, push, deploy, or change production services without the final deployment step and explicit scope.
